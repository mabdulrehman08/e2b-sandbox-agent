# Sandbox Loop

**Built for E2B’s Product Engineer (Backend) role:** a coding-agent customer needs to run model-generated programs without giving those programs access to the application server, its files, or its credentials. This demo exercises that exact workload: generate Python → execute in E2B → inspect results → repair → execute again.

The model writes arbitrary executable code. Even a well-intentioned agent can delete files, leak secrets, exhaust memory, or loop forever. A prompt cannot enforce a security boundary. The host owns the model connection and expected answers; disposable E2B sandboxes own execution. The backend work here is managing that boundary, execution lifecycle, feedback, and failure budgets.

## Run

Python 3.11+, an [E2B API key](https://e2b.dev/dashboard), and an [Anthropic API key](https://platform.claude.com/) are required. This uses the `e2b` SDK directly, with its default `base` template, and Claude Opus 5.5 for source generation and repair. Runs consume sandbox and model API credits.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Set E2B_API_KEY and ANTHROPIC_API_KEY in .env.
python demo.py
```

Three tasks run end to end: merging intervals, counting and ranking words, and shortest paths in cyclic graphs. Each has four concrete cases, including empty inputs, ties, containment, and unreachable nodes. A correct first attempt ends immediately; a failed attempt sends actual inputs, expected answers, stdout, stderr, and exit status back to the model. The model returns a full replacement program, up to three attempts per task.

To make a repair visible, start each task with an intentionally incorrect implementation:

```bash
python demo.py --exercise-repair
python demo.py --task shortest-path --exercise-repair --max-attempts 3
```

Only the first candidate in repair mode is supplied by the demo; every repair is generated by the live model. There is no canned success or simulated sandbox path. Set `ANTHROPIC_MODEL` to change the model.

The terminal shows sandbox IDs, pass counts, failures, and final status. `runs/<timestamp>/<task>/` contains each candidate `.py` and a JSON report with actual execution results. Source artifacts are for inspection: execute them only in a sandbox. Exit codes: `0` all tasks solved, `1` an unsolved task or API failure, `2` missing credentials. A model is not guaranteed to solve within the budget.

## What it proves

- **Real SDK integration:** `Sandbox.create`, `files.write`, `commands.run`, nonzero exit handling, and `kill`. Python is executed remotely through OS commands rather than a local `exec`.
- **Bounded lifecycle:** a fresh sandbox per attempt, 90-second sandbox TTL, five-second per-case process deadline, CPU/memory/file limits, remotely capped output reads, and cleanup in `finally`. At most nine sandboxes for the default three-task run.
- **Useful iteration:** host-side JSON validation determines success. Expected answers never enter the sandbox, so replacing a test file or printing “passed” cannot satisfy the evaluator. Saved reports make failures reviewable.
- **Secret and network separation:** API keys stay in the host process and are never passed as sandbox environment variables. Internet access is explicitly disabled. No host directory is mounted, and generated source is never interpolated into a shell command. Each retry starts without files or processes from its predecessor.

Isolation protects the host; it does not make everything inside the sandbox trustworthy. The candidate can still affect other files in its own sandbox, and these finite tests establish correctness only for the listed cases. Sandbox output also remains untrusted model input; the system prompt labels it accordingly, but that alone is not a prompt-injection defense. Process limits complement the disposable sandbox boundary rather than replace it.

## Verify

```bash
python -m unittest -v
```

Credential-free tests verify feedback-driven retry, attempt exhaustion, JSON/exit-status validation, timeout feedback, and cleanup after transport failure using SDK-compatible mocks. They do not claim to test E2B’s isolation. `python demo.py --exercise-repair` is the live integration check and requires both keys. During development, dependencies and SDK signatures were verified and the local tests passed; live execution was not verified because credentials were unavailable.

Implementation: `agent.py` is the loop and E2B executor, `tasks.py` defines contracts and cases, and `demo.py` runs the suite.
